# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pjPlanner: a team planning tool. Modules (with groups, API items, colors/icons, canvas positions) and directed relations between them, drawn as a graph; plus an issue tracker (epic/story/bug/task) and sprints. No auth, ever (open team platform). Multiple projects: everything is scoped by `project_id`, exportable/importable as JSON.

Three independent npm packages (no workspace root):
- `backend/` — Node 22+ (better-sqlite3@13 segfaults on Node 20), Fastify 5, better-sqlite3. Also serves the built frontend (`STATIC_DIR`) and the MCP bundle/skill.
- `frontend/` — Vite + React 18, `@xyflow/react` for the graph, `dagre` for auto layout.
- `mcp/` — stdio MCP server, a thin client over the REST API; bundled with esbuild to a single `dist/pjplanner-mcp.mjs` that the backend serves for download.

## Commands

```bash
make install            # npm install in backend + frontend
make dev-backend        # tsx watch, port 3030
make dev-frontend       # Vite dev server
make build              # tsc backend; tsc --noEmit + vite build frontend
make build-mcp          # build + bundle mcp (needed locally for /api/mcp/download)
make test               # backend + frontend vitest (mcp tests: cd mcp && npm test)
make up / down / redeploy / logs   # docker compose (redeploy = down + up --build) (data in pjplanner-data volume)
```

Single test: `cd backend && npx vitest run test/api.test.ts -t "name pattern"` (same pattern in `frontend/` and `mcp/`). Frontend type-check is part of `npm run build` (`tsc --noEmit`).

Backend env: `PORT`, `WRITE_KEY` (both from `.env`), `DB_PATH`, `STATIC_DIR`, `PUBLIC_URL` (LAN URL shown in "Connect agent", needed in Docker), `JIRA_WRITE` (master switch for writing to Jira), `MCP_BUNDLE`, `MCP_SKILLS`.

## Architecture

**Backend** (`backend/src/`): `app.ts` exports `buildApp(dbPath)`, which only wires things together: `db/open.ts` opens SQLite and runs the idempotent startup migrations (`openDb`, `db/migrations.ts`; schema changes must be additive/migrating since existing DBs exist), `plugins/` registers cross-cutting hooks (write-key auth, project scoping, error handler, static frontend) and `routes/` registers one file per domain (modules, owners, groups, relations, graph, issues, sprints, projects, projectTransfer, jira, system). Each domain file exports a `xxxStore(db)` factory (row mappers, getters, parsers) that other routes reuse, plus `xxxRoutes(app, db)`. `jira.ts` is the Jira client. `index.ts` only listens. Tests call `buildApp(':memory:')` and use `app.inject`. `errors.ts` holds `HttpError`/`bad`/`notFound` and `validation.ts` the body helpers (`obj`, `str`, `colorField`, `iconField`, `id`); all errors serialize as `{"error": {"code", "message"}}` (may carry an optional nested `extra` object, e.g. `error.extra.jiraUpdated` on the Jira update conflict) with codes `validation_error` (400), `not_found` (404), `conflict` (409), `internal_error` (500).

Key semantics (full contract in README "API" section — keep README in sync when changing the API):
- `PUT` on modules/owners/groups: omitted field = unchanged, `null` = clear. `PUT /api/issues/:id` is a **full** update.
- Module `apiItems` are replaced wholesale in one transaction (no item endpoints).
- Groups nest via `parentId` (max depth 4, no cycles); deleting a group moves children up and ungroups modules.
- Issue types are `epic`, `story`, `bug`, `task` (old subtask rows migrate to task). Epic holds stories/bugs/tasks, story and bug hold tasks; only tasks may carry module, assignee (any owner; modules have no owners, `module_owners` is dropped on startup) and sprint. `rollupModuleIds` = own module + descendants'.
- Issue states: `open` -> `code_review` -> `test_validation` -> `closed`. Only `closed` is finished; everything that used to test `state = 'open'` means "unfinished" and tests `state <> 'closed'`. The `issues.state` CHECK was widened by `migrateWorkflowStates` (rebuilds the table; runs after every column exists).
- Sprints: planned → active → closed, only one active; activating auto-assigns owners to unassigned tasks (`balanceOwners` in `routes/sprints.ts`: all tasks under one story/bug go to one person; otherwise the least-loaded owner by estimates, minus a saturating bonus for tasks that owner closed before in the same modules, i.e. module experience), closing sends open tasks back to the backlog.
- Projects: a fresh DB has none (users create them; data routes 404 with code `no_project` until then; pre-projects data migrates into "My project"). The active project of a request comes from the `x-project` header (`?project=`), held in `AsyncLocalStorage` (`P()` in `context.ts`); any new query on modules/owners/groups/issues/sprints must filter by `project_id = P()` (relations/API items inherit it via their module). Frontend `api.ts` sends the header from localStorage; MCP uses `PJPLANNER_PROJECT`. Export/import: `GET /api/projects/:id/export`, `POST /api/projects/import` (always a new project, ids remapped).
- Jira (import, plus explicit upload/update and a per-issue refresh that pulls title/description/state, needing only Jira enabled): `JIRA_URL`/`JIRA_TOKEN` in `.env` only. A project stores `projects.jira_jql` and optional `projects.jira_label` (the label that marks importable issues, ANDed onto the JQL by `effectiveJql`) (a JQL string the user writes, with field names; never a `customfield_` id, those differ per instance) and imported issues carry `issues.jira_key`. Pure rules (type/state mapping, parent resolution) live in `backend/src/jiraSync.ts`; `jira.ts` is the HTTP client; routes in `routes/jira.ts` and `routes/jiraImport.ts`. Writes to Jira happen only through `routes/jiraExport.ts` (`POST /api/issues/:id/jira/upload|update`, one issue per click), and only when `JIRA_WRITE=1` AND the project's `projects.jira_write` is on; never bulk or automatic. Descriptions written to Jira get a trailing italic `_Updated from pjPlanner_` footnote (`addFootnote`/`stripFootnote` in `jiraSync.ts`), stripped on every pull. Upload opens a form in the UI fed by `GET /api/issues/:id/jira/upload-form` (Jira createmeta for the project and type). Which extra fields the form shows is configurable per project: `projects.jira_upload_config` (`jiraUploadConfig`, JSON `{hidden, defaults}` keyed by Jira field id, never exported/imported; pure helpers `parseUploadConfig`/`applyUploadConfig`/`withHiddenDefaults` in `jiraMeta.ts`): the form marks fields `default`/`hidden`, a required field without a usable default stays visible, and upload merges the defaults of hidden fields; `GET /api/jira/create-fields` feeds the settings UI (needs Jira enabled only; the one `/api/jira/*` route that is project-scoped). Upload adopts a same-type-and-title Jira issue found by the project filter instead of duplicating; update pushes only summary, description and labels and fails closed on conflicts (`issues.jira_synced_at` vs Jira `updated`, `force` overrides). `jiraWrite`, `jiraUploadConfig` and `projects.jira_project_id` (`jiraProjectId`, a Jira project id or key set per pjPlanner project; digits are sent as `project.id`, anything else as `project.key`) are never exported/imported. Upload target: a parent in Jira -> the parent's Jira project (key minus number), label, linked; parent not in Jira -> 409; a task is always created as Jira type Task, never Sub-task: under an epic it gets the Epic Link, under a story/bug it is created without `parent` and then linked to it via `/rest/api/2/issueLink`, default link type `Relates`, chosen with `linkType`; a failed link leaves the issue created and answers `linkWarning`); root epic/story/bug/task -> `jira_project_id` with the label and no link (409 when unset). Each project also has `projects.jira_enabled` (`jiraEnabled`, default off, set on by migration when a filter exists, never exported/imported): when off, import and all writes answer 409 and data is kept. Agents must not write to Jira outside these endpoints.
- Write key: config comes from `.env` at the repo root (`.env.example`; `PORT`, `WRITE_KEY`, `PUBLIC_URL`), loaded by `backend/src/index.ts`, compose and the Vite proxy. When `WRITE_KEY` is set every non-GET `/api` request, UI and agents alike, needs `x-api-key` (else 401); unset = open (tests rely on this; `index.ts` refuses to start without it). The UI is read-only until unlocked via the header lock (`LockButton`, key in localStorage). On top of the key, `plugins/editorLock.ts` keeps one in-memory editor lease per project (UI tabs send `x-client`; others' writes answer 409, agents without it are exempt) and streams `changed`/`editor` events over SSE (`GET /api/events`) that `App.tsx` uses to refresh live.

**Frontend**: `App.tsx` holds the loaded graph/issues/sprints state and hash routing (`route.ts`: diagram, owners, groups, issues, sprints). `api.ts` is the fetch wrapper; `types.ts` mirrors backend payloads. Graph rendering in `components/GraphView.tsx` with custom edge routing (`edgeRouting.ts`, `RoutedEdge.tsx` — floating arrows attached at nearest card border, reverse pairs curved apart), group boxes derived from member cards (`groupBoxes.ts`), snap guides, dagre layout (`layout.ts`). Editing happens in modal popups (`Modal.tsx`); dirty modals block navigation. Saved colours live in localStorage, not the DB. Tests in `src/__tests__/` (vitest + jsdom + Testing Library).

**MCP**: `mcp/src/tools.ts` defines tools (read tools always; write tools only when `PJPLANNER_API_KEY` is set), `api.ts` calls the backend, `deps.ts`/`sprint.ts` compute transitive dependencies and sprint groupings. `mcp/skills/<name>/SKILL.md` is a suite of agent skills served to users (`/api/mcp/skills`): `pjplanner-map` maps a codebase into modules, `pjplanner-breakdown` breaks stories into tasks. Adding a skill = a new folder there plus an entry in `SKILLS` in `McpDialog.tsx`.
